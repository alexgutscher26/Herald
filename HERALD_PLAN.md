## 0. How the two plans fit together

They answer different questions and must not drift apart:

| Document           | Answers                                                                                                                                    | Changes when                                        |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| [plan.md](plan.md) | What UserJot has, how Herald compares, the target data model, 147 capability rows, parity phases and estimates                             | UserJot research or the target architecture changes |
| This file          | What Herald will do next, what is explicitly out of scope, the current baseline, workstreams, acceptance gates and the improvement backlog | Weekly, as work lands and decisions are made        |

Rules for keeping them in sync:

1. **plan.md is the UserJot parity source of truth; §8.1 is the Featurebase parity source of truth.** Workstreams below reference both; they do not repeat all 147 UserJot rows or the 51 Featurebase rows.
   1a. **A Featurebase row carries the same weight as a plan.md row.** It enters a workstream here or is refused in §14; it is never left floating as a good idea.
2. **This file is the execution source of truth.** A capability is not done because it appears in plan.md; it is done when the gate in this file passes.
3. **Every work item traces to a parity capability or an improvement.** If it traces to neither, it is out of scope until deliberately added to both.
4. **No silent scope reduction.** If a parity item slips, mark it `Deferred` here with a reason and a revisit date; do not delete it from plan.md.
5. **No mock data, ever.** Pages read PostgreSQL; tests use factories against a test database; no demo workspace is shipped.
6. **Update both documents at milestone boundaries.** A new capability goes into plan.md §4 and into a workstream here; a completed capability gets evidence here.

Status vocabulary used in this file:

- **Done** — reads and writes real PostgreSQL, is authorized, tested, and has no placeholder copy.
- **Partial** — the data model or internal version exists, but the customer-facing or automated half does not.
- **Placeholder** — a route exists and honestly says it is unavailable. This is not a feature.
- **Not started** — no model, route or implementation.
- **Deferred** — deliberately not in the current milestone; reason and revisit date recorded.

### What must not regress

- Transactional, status-guarded publishing with idempotent delivery rows (`publisher.ts`).
- Composite foreign keys that make cross-product links impossible (`release_feedback_links`); the roadmap is a projection of `feedback_posts.status`.
- Closed-by-default cron auth with constant-time comparison.
- Explicit publish-vs-schedule flow and timezone handling in the release editor.
- Deny-by-default permissions and tenant-scoped resolution in `authz.ts`.
- Real database metrics and honest empty states. No fabricated numbers, no demo mode, no seed data.
- The release↔cancellation-reason differentiation. It is not UserJot parity and should not be deleted while chasing parity.

## 3. Definition of done

### Every shipped item

- **Authorization:** the check is on the server; hiding a button is never the boundary.
- **Tenant isolation:** every read and write resolves through workspace → product → board; a guessed id from another tenant returns 404, not another tenant’s data.
- **Real data:** reads and writes PostgreSQL. No mock arrays, no `demo` store, no hard-coded metrics.
- **Migration:** forward-only SQL, reviewed, with a backfill reconciliation query and a rollback note.
- **States:** loading, empty, error, unauthorized and not-found are designed, not left to a generic boundary.
- **Accessibility:** keyboard reachable, visible focus, labelled controls, sensible heading order. Public pages target WCAG 2.2 AA.
- **Responsive:** usable at 360 px, tablet and desktop; no horizontal scroll for primary flows.
- **Tests:** pure logic has unit tests; writes/reads have integration tests against a real Postgres; each critical path has at least one end-to-end test.
- **Observability:** failures are logged with enough context to debug; background jobs record attempts and errors.
- **Docs:** environment variables, routes, permissions and operational steps are updated in `README.md` or an ADR.
- **No leftovers:** no commented-out implementation, no “temporary” public endpoint, no placeholder copy in a page that claims to work.

### Milestone gate

- The exit criteria in plan.md §7 for the matching phase are met.
- The scenarios in plan.md §9 that belong to the milestone pass manually and, where practical, in Playwright.
- `bun run typecheck`, `bun run lint`, `bun test` and `bun run build` are green.
- No open P0 bug; no known cross-tenant leak; no unhandled 5xx in the demo path.
- A demo script runs from a clean database through the milestone’s main flow.
- `README.md` reflects the real state; placeholder routes are either implemented or hidden from primary navigation.

### Placeholder rule

`SectionUnavailable` is honest and useful while a section is being built, but it is not a feature. A milestone cannot claim a section complete while its route renders a placeholder. If a section is not in the milestone, hide it from primary navigation rather than shipping a dead end in the main product.

### No-mock rule

- No demo feature module, mock fixtures, `faker` data or seeded production content.
- Tests may use factories and fixtures, but only against a test database.
- Any new mock import fails CI. Add a narrow grep guard for known demo/mock modules and review it when the test harness lands.

## 4. Priority and sequencing

| Priority | Meaning                                                                     | Examples                                                                               |
| -------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **P0**   | Blocks the customer loop, or is a security/data-correctness issue           | Customer identity, boards, public resolver, jobs/email, public feedback, notifications |
| **P1**   | Required for a credible paid product and parity                             | Widget, conversations, Juno, API/MCP, plans/settings, most P1 rows in plan.md          |
| **P2**   | Retention, polish or differentiation; may follow the first sellable release | Visitor map, live translation, identity masking, advanced prompts, Swift SDK           |

Sequencing rules:

1. **Foundation before surface.** W0 precedes every customer-facing workstream.
2. **Customer loop before widget.** W1 and W2 must work in a plain browser before W3 embeds them.
3. **Conversations before Juno.** W5 needs threads, handoff and operator state from W4.
4. **API after domain services.** W6 starts after W1/W2 so it exposes real behavior, not stubs.
5. **Billing does not block the loop.** Entitlements are modeled in W0; Stripe can land in W7.
6. **Win-back does not block parity.** W8 starts after M2 and can run in parallel with W4–W7.
7. **Cut P2 before P1; never cut tests, authorization or migration safety to hit a date.**

## 5. Workstreams

### W0 — Foundations and safety

**Priority:** P0 · **Estimate:** 2 weeks · **Milestone:** M0 · **Parity:** [plan.md](plan.md) §5, §6.1–6.2, Phase 0

**Goal:** create the one customer/board/public/job model that every later feature depends on, without disturbing the existing dashboard.

**Capacity note:** if W0 takes a third week, take that time from later P2 scope; do not split the identity migration or skip the integration-test harness.

**Build**

- [x] **Customer identity.** `customers`, `customer_companies`, `customer_company_memberships`, `customer_sessions`. Workspace-scoped, with nullable `external_id`, normalized email, traits JSON, verified/banned timestamps and last-seen. — migration `0002_cold_iceman.sql`
- [x] **Boards and feedback extensions.** `boards` with visibility, moderation settings, guest-posting and position; `board_tags`, `feedback_tag_links`, `feedback_followers`, `feedback_reactions`, `feedback_attachments`, `moderation_reviews`, `blocked_customers`. — migration `0002_cold_iceman.sql`; `feedback_posts.board_id` added nullable for the backfill
- [x] **Backfill.** Create a default board per product, move every existing feedback post to it, map the current statuses to the six-state model, add nullable `author_customer_id` while keeping `author_id` for team attribution. — migration `0003_jazzy_queen_noir.sql`; `declined` folded into `closed`; new products get a default `feedback` board at onboarding
- [x] **Public tenant resolver.** Host/path → workspace → product → board without a session. Unknown or private returns 404. Add a `public/` query module and serializers; public pages never import the dashboard snapshot. — path resolution at `/p/{workspace}/{product}/{board}`; custom-host mapping stays in W7 per D4; projections served from `/api/public/boards/...`
- [x] **Customer session.** Signed httpOnly cookie, short-lived, guest mode without an email until supplied, `identify`/logout, origin and CSRF checks on writes, rate limiting. — 24h HMAC cookie, hashed tokens rotated on identify, durable Postgres rate limits, `/api/public/session/*`
- [x] **Jobs and outbox.** `jobs` table with `run_at`, `locked_at`, `attempts`, `last_error`; `FOR UPDATE SKIP LOCKED`; bounded batches; a protected cron runner. Migrate release publishing to a job type while preserving the existing endpoint contract; add `deliver-notification`, `send-email`, `process-import`, `crawl-knowledge`, `deliver-webhook`, `recalculate-trending`. — migration `0004_brave_dexter_bennett.sql`; claiming, backoff, stale-lock reclaim and the runner live in `src/features/jobs/` behind `GET|POST /api/cron/jobs`; publishing is the `publish_releases` job under the unchanged `/api/cron/publish-releases` contract. Handlers exist for `publish_releases`, `send_email` and `deliver_notification`; the other four enum values fail loudly until their feature lands. A job enqueued for “now” takes its `run_at` from the database clock rather than the application's, so a small clock skew cannot hide a fresh job from the runner.
- [x] **Email outbound.** One provider adapter, templates, suppression list, test send, delivery status updates. Inbound parsing belongs to W4. — Resend HTTP adapter without an SDK dependency (`src/features/email/provider.ts`), HTML/text templates, per-workspace suppression keyed on the normalized address, test-send server action behind `settings:manage` and a per-user rate limit (no Settings UI yet), `pending`/`sent`/`skipped`/`failed` status updates on the existing outbox. `RESEND_API_KEY` and `EMAIL_FROM` are optional as a pair; unset means email stays disabled with a non-retryable error rather than a silent no-op.
- [x] **Storage.** A storage abstraction for covers and attachments, signed URLs, MIME/size limits, checksums. — `StorageProvider` boundary with a checksum-verifying local driver, magic-byte sniffing instead of trusting the declared type, per-kind size limits, generated keys that cannot escape the root, and HMAC-signed downloads at `/api/storage/{key}` (404 on any invalid signature). Uploading from the release editor and feedback composer stays in W1.
- [x] **Entitlements and feature flags.** A typed plan config and server-side gate functions; no billing yet. Flags for public routes and the widget. — `workspaces.plan` (`free` | `pro`, migration `0005_open_magma.sql`), pure catalogue and `checkUsage` in `src/features/entitlements/plans.ts`, database-resolved gates and usage counts in `entitlements.ts`, and `FLAG_*` kill switches in `flags.ts`. The public board API and customer-session bootstrap require the flag **and** the plan feature and answer 404 otherwise. No billing surface: a plan change is a database update.
- [x] **Observability baseline.** Request ids, structured server logs, job run history, error tracking. A failed job must be visible without reading the database by hand. — `src/proxy.ts` stamps a sanitised `x-request-id` on every request and response; `src/lib/logger.ts` writes one redacted JSON line per event; `error-report.ts` logs first and forwards to the optional `ERROR_WEBHOOK_URL`; `job_runs` records every runner invocation and `GET /api/cron/jobs?view=history` lists runs plus exhausted jobs. **Build**

- [x] **REST API v1.** Boards, requests, comments, votes, tags, changelogs, members, companies, conversations, messages/notes. Bearer tokens hashed at rest, scoped per workspace. — `/api/v1/*` routes through one router; tokens are `hrl_` secrets stored as SHA-256 with `read`/`write` scopes, and the workspace comes from the token row ([token.ts](src/features/api-v1/token.ts), [auth.ts](src/features/api-v1/auth.ts)). Pinned by [tests/integration/mcp.test.ts](tests/integration/mcp.test.ts).

The job uses the configured AI provider to choose an active board and title, falling back to the first line and first board if AI is unavailable; it writes `source = 'slack'` and a `slack_request_links` row. ## 10. Metrics and review cadence

### Weekly operating rhythm

- **Monday:** update §13 status, confirm the week’s milestone slice, surface blockers.

- **Friday:** demo the milestone slice on a clean database; record evidence; update both plans.

- If M1’s end-to-end scenario fails, stop and fix it before starting W3.

- If the integration test database is not working, do not merge identity/board migrations.
- If a milestone’s P2 items are the only thing left, ship the P0/P1 gate and defer them explicitly.

## 11. Risks and mitigations

| Risk                                                 | Impact                                 | Mitigation                                                                                                |
| ---------------------------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Two plans drift                                      | Conflicting scope and priorities       | §0 sync rules; weekly update; every item traces to a section                                              |
| Customer identity migration breaks existing feedback | Data loss or broken votes              | Nullable columns, transactional backfill, reconciliation, keep team attribution, dual-read during rollout |

## 14. Deferred and explicitly out of scope

These are deliberate. Add a revisit date before promoting any of them.

- **Native mobile apps** for Herald itself. The web widget is the integration surface; a Swift SDK can follow only if customers ask.
- **UserJot v2 widget compatibility.** Herald has no installed base; build v3 only.
- **Custom statuses.** Six fixed statuses keep the roadmap projection, notifications and API predictable.
- **Per-seat billing.** Flat workspace plans match the market and avoid seat-metering complexity.
- **General-purpose help desk.** Conversations stays product-support scoped: no SLA engine, macros marketplace or social inbox.
- **Full product-analytics suite.** Board/conversation/Juno metrics only; no session replay, funnels or heatmaps.
- **Visual clone of UserJot.** Implement capabilities, not brand, copy, pricing-page layout or assets.
- **Demo/mock workspace.** Test fixtures only; a real workspace created through onboarding is the only demo.
- **Visitor map and live translation** until after a privacy review and the core support loop works.
- **Linear parity** until the exact behavior is verified against UserJot’s docs; do not build from a logo on a pricing page.
- **Custom statuses** stay six fixed states (restated by the Featurebase scan, which lets customers configure them). The roadmap projection, notifications and API all key off the six.
- **Per-resolution AI billing** and **seat-metered “lite” billing.** Herald sells flat plans with a cost meter (§12 D8 stands); usage pricing needs contracts and metering work that does not pay for itself yet.
- **Call-recorder and voice integrations** (Gong, Granola, Fathom, Fireflies, Grain, tl;dv). Transcript ingestion, per-provider contracts and consent handling; revisit only when a customer asks by name.
- **WhatsApp, Microsoft Teams and a Discord bot.** Each channel carries its own policy, identity and moderation surface; email, Slack and the widget are the supported channels until demand is proven.
- **Multi-brand workspaces.** One workspace, one brand keeps the tenant, domain and sender model unambiguous; this is a tenancy change, not a theme.
- **AI inbox translation.** Message text leaving the workspace still waits on the privacy review that already blocks live translation.
- **A native mobile app for Herald itself.** Unchanged from the existing entry above; the responsive dashboard and widget remain the mobile story.
