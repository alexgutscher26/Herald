## 0. The honest state of the product

Herald is much further along than the older plans claim. The dashboard covers releases, feedback,
boards, roadmap, moderation, conversations, help center, API docs, widget, surveys, tours/banners,
outbound, subscribers, win-back, analytics, operations, integrations, import/export and settings.
Public surfaces include boards, requests, submit, roadmap (with views), changelog, help, docs, search,
notifications, preferences, support, surveys and an embed shell. There is a REST API, MCP server,
webhooks, Slack, five issue trackers, HubSpot/Salesforce CRM sync, billing, SCIM, SAML settings,
a viewer role, and a real Postgres test harness with 63 integration suites.

So the remaining work is not "build the product". It is:

1. **Prove it works in a browser** — the last recorded browser pass (HERALD_PLAN.md §13.1) found every
   `/app/*` route stuck on its loading skeleton and the widget thread loading a 404. That record is
   from 2026-11-06 and may be stale, but it has never been formally re-run and closed.
2. **Close the security/ops basics** — no CSP or security headers, no error tracking (Sentry/APM),
   no dependency audit, no e2e suite.
3. **Finish the account lifecycle** — no password reset, no email verification, no 2FA.
4. **Remove the remaining fakes and dead ends** — base64 release covers in the database, two job enum
   values with no handler, `data-url` uploads that bypass the storage module.
5. **Then** add depth: prioritisation, insights, translation, reporting, realtime, deeper AI.
